# Linux input provenance

**Timestamp:** 2026-07-30 18:46 +08

## Core Decision/Topic

Implement Linux self-injection provenance for both supported backends while
preserving `InputOrigin::Unknown` whenever the backend lacks positive evidence.
The goal is to let a remote-input host drop events injected by the same Monio
process without claiming that every other event is physical.

## Options Considered

- Leave Linux events as `Unknown` and rely on application-level timing or value
  matching. Rejected because scheduling delays and coincident physical input
  make those heuristics unsafe.
- Use device names to identify Monio's evdev/uinput injector. Rejected because
  uinput names are caller-controlled and can be imitated.
- Require evdev/uinput for all Linux sessions. Rejected as the only solution
  because it requires access to `/dev/input` and `/dev/uinput`, while the
  existing X11 backend otherwise works as an ordinary desktop user.
- Keep X11 provenance unsupported because XTest device events carry no custom
  tag. This remains the simplest fallback, but XRecord can also identify the
  client that issued each XTest request and preserves server event ordering.
- Use Wayland InputCapture/RemoteDesktop portals and libei. This remains the
  preferred future Wayland desktop architecture, but it is a separate backend
  with compositor-controlled sessions and is not implemented in this change.

## Final Decision & Rationale

For evdev/uinput, Monio owns one process-scoped virtual device and retains the
exact live character-device number of its `/dev/input/event*` node. Capture
classifies events by `fstat` on the already-open file descriptor. Listen mode
marks only that device as `ThisMonioSession`; grab mode excludes it to avoid
re-injection feedback. This uses kernel-backed identity instead of spoofable
metadata.

For X11, Monio owns one persistent XTest display connection. Its X11 resource
ID base identifies the injector client. XRecord captures both device events and
`XTestFakeInput` requests; requests from that exact client are correlated with
the resulting device events in server order. Event type and key/button detail
must match. A mismatch clears pending state and returns `Unknown`, avoiding
timing-window guesses.

This keeps X11 unprivileged and makes it the practical default on a native X11
desktop. evdev remains appropriate for Wayland, headless operation, exact
device-level capture, or real suppression, but requires explicit device
authority.

## Key Changes Made

- Added exact evdev injector identity tracking in
  `src/platform/linux/evdev/provenance.rs`.
- Created the evdev virtual injector before device enumeration, retained
  per-device origin, and excluded the exact injector from grab capture.
- Improved evdev permission and injector-node resolution errors.
- Added X11 request correlation in
  `src/platform/linux/x11/provenance.rs`.
- Reused a persistent, mutex-serialized XTest connection for every X11
  simulation path.
- Extended the XRecord range to observe XTest requests and assigned matched
  events `InputOrigin::Injected { ThisMonioSession }`.
- Updated README guidance, Linux permission notes, backend recommendations, and
  the cross-platform provenance handoff.
- Generalized the `ThisMonioSession` documentation so it describes
  backend-specific evidence rather than only the macOS tag/PID mechanism.

## Verification

- A native XRecord/XTest protocol probe observed the known injector request
  immediately before its matching device event with the same server time.
- `cargo run --example synthetic_input_detection` passed twice on GNOME X11:
  ControlLeft press/release and pointer target/restoration were all classified
  as `ThisMonioSession`.
- `cargo test --all-features --lib`: 15 passed, 0 failed.
- `cargo check --all-features`: passed.
- `cargo clippy --all-features --lib -- -D warnings`: passed.
- `cargo fmt --all -- --check`: passed.
- `cargo doc --all-features --no-deps`: passed.
- Context7 resolved the official X.Org documentation and confirmed the XRecord
  request timing and device-event ordering assumptions.
- Full all-target Clippy remains blocked by two pre-existing
  `unnecessary_map_or` warnings in `examples/grab.rs`.
- The evdev runtime diagnostic could not run in the Codex device namespace,
  which exposes neither `/dev/uinput` nor `/dev/input/event*`. Earlier direct
  host execution reached `/dev/uinput` but lacked permission.

## Future Considerations

- Run the privileged evdev acceptance matrix with both Monio and an unrelated
  uinput device, listener restart, hot unplug/recreation, and grab feedback.
- Verify X11 classification against a concurrent unrelated XTest client and
  under high-rate pointer, button, and wheel traffic.
- Characterize X11 server-generated key autorepeat. Repeats without a matching
  XTest request must remain `Unknown` unless stronger evidence is found.
- Repeat X11 verification on another Xorg version and Xwayland; do not describe
  Xwayland as a complete native Wayland backend.
- Implement and validate a portal/libei backend on native GNOME and KDE before
  claiming broad unprivileged Wayland support.
- For a shipped evdev desktop product, prefer a constrained privileged helper
  over adding every user permanently to the broad `input` group.
